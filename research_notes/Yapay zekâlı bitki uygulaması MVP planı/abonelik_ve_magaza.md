# Subscriptions and store compliance for a Turkish AI plant app (Expo + NestJS), as of October 2026

Scope: picking the subscription stack (RevenueCat vs. direct StoreKit 2 / Play Billing through expo-iap or react-native-iap with our own NestJS verification), how to handle receipts securely on the server, App Store and Google Play rules that apply to an AI plant app (identification, diagnosis, AI chat, reminders) selling one digital subscription, paywall and trial benchmarks, and care-reminder notifications. Assumes a Turkish legal entity on both stores. Research date: 2026-10-25.

---

## 1. Stack choice: RevenueCat vs. direct StoreKit 2 / Play Billing (expo-iap / react-native-iap) with our own verification; Expo SDK versions

### Takeaway
The current Expo SDK is **58** (released 2026-10-15, React Native 0.88, iOS 16.4+, Android 7+). Going from SDK 50 means crossing the SDK 55 cutoff, where the Legacy Architecture was dropped. **react-native-iap no longer supports Expo** (from v15), so the direct route in Expo means **expo-iap** (SDK 53+). For an MVP, RevenueCat is the low-effort default: it is free under $2.5K monthly tracked revenue (MTR) and costs 1% of all MTR above that. Building on expo-iap with our own NestJS verification avoids the fee but means implementing App Store Server API + ASSN V2 + Play Developer API + RTDN ourselves.

### Inferences
- **Upgrade path from SDK 50.** The Legacy Architecture ends at SDK 54, and SDK 55 removes expo-av. The safest path is staged: (1) SDK 50 → 54 one SDK at a time, migrating expo-av, (2) turn on the New Architecture on SDK 54 and check every native dependency, (3) jump to SDK 57 or 58 with a fresh dev build. **SDK 57** is the practical choice today: it is what `create-expo-app` uses until Expo Go for 58 ships, and expo-iap is validated on it. SDK 58 is fine with dev builds only (needed for IAP anyway), but its SceneDelegate migration and the Expo Router rework are extra risk. Both satisfy Play's API 36 requirement (targetSdk 36).
- **Minimum OS impact.** SDK 56+ requires iOS 16.4+ and Android 7+, so iPhones that cannot run iOS 16 (iPhone 7 and older) are dropped. This is acceptable for a new app.
- **RevenueCat pros:** one SDK for both stores; server-side receipt validation, ASSN V2 / RTDN ingestion, grace period, billing retry, refund, and family-sharing state handled for us; webhooks we can mirror into NestJS (entitlement table); remote-configurable paywalls and experiments; benchmark dashboards; Customer Center (cancellation and refund flows). **Cons:** 1% of gross once MTR ≥ $2.5K; vendor lock-in for subscriber history (export is possible); one more data processor to disclose (KVKK/GDPR and store privacy labels); a dependency on RevenueCat uptime for entitlement checks unless we cache entitlements in NestJS.
- **Direct (expo-iap + NestJS) pros:** no revenue share; full data ownership; the purchase is bound to our `userId` via appAccountToken / obfuscatedAccountId. **Cons:** we must build and maintain JWS verification, App Store Server API calls, an ASSN V2 endpoint (separate sandbox and production URLs), a Google service account with the Play Developer API, a Pub/Sub topic and push subscription for RTDN, acknowledgement within 3 days, a reconciliation job, and the full state machine (section 2). This is likely several engineer-weeks plus ongoing upkeep for each store API change (PBL 8 → 9, iOS 27). At 1%, RevenueCat costs $25/month at $2.5K MTR and $100/month at $10K MTR, which is far less than the engineering time for an MVP.
- **Recommended MVP pattern:** RevenueCat SDK in the app, identified with our NestJS `userId` as the App User ID right after login. RevenueCat webhooks go to NestJS (verify the auth header, store events idempotently by event id), and NestJS keeps its own `entitlements` table that the AI endpoints check. That way paid-only server features (AI chat, diagnosis quota) are not gated only on the client. If we later outgrow RevenueCat, the same table can be fed by our own ASSN V2 / RTDN handlers.

### Gaps
- No official RevenueCat statement found for the minimum Expo SDK or iOS version of the current `react-native-purchases` major. The Expo install page states none.
- The SDK 58 changelog does not state the Android minSdk number. "Android 7+" means API 24 (expo-iap docs also say API 24).
- Did not verify on Google's own deprecation page whether PBL 8 can still be used for new updates after 2027-08-31.
- Turkey-specific payout and banking details (TRY vs. USD payouts, Turkish withholding or e-invoice rules for store revenue) were not researched. A Turkish accountant should confirm.

## 2. Security pitfalls in server-side receipt handling

### Takeaway
Bind each purchase to our account at purchase time (Apple `appAccountToken` UUID, Google `obfuscatedAccountId`) and verify on the server that the binding matches the logged-in user. Treat Apple `originalTransactionId` and Google `purchaseToken` as **unique keys**, so one store purchase cannot unlock several accounts. On every notification, re-fetch the authoritative state from the store API instead of trusting the notification type. Handle sandbox and production explicitly, because App Review purchases are sandbox purchases against our production backend.

### Cited Findings

**Apple: binding to accounts**
- `appAccountToken` is a **UUID** we generate and pass at purchase time (`Product.PurchaseOption.appAccountToken(_:)`). The same token may be used on many transactions, for example one per customer — [Apple: Set App Account Token](https://developer.apple.com/tutorials/data/documentation/appstoreserverapi/set-app-account-token.json)
- **Set App Account Token** endpoint, introduced at WWDC25: `PUT https://api.storekit.apple.com/inApps/v1/transactions/{originalTransactionId}/appAccountToken` (sandbox: `api.storekit-sandbox.apple.com`). It sets the token for purchases made outside the app (e.g. offer code redemptions in the App Store) or updates an existing one, and **overwrites** any existing token. It must use an *original* transaction ID. **Not supported for Family Sharing transactions** (`inAppOwnershipType = FAMILY_SHARED`). For subscriptions the token applies to the current and future renewals and carries over on upgrade, downgrade, or crossgrade. Errors include `FamilyTransactionNotSupportedError`, `TransactionIdIsNotOriginalTransactionIdError`, and `InvalidAppAccountTokenUUIDError` — [Apple: Set App Account Token](https://developer.apple.com/tutorials/data/documentation/appstoreserverapi/set-app-account-token.json); [WWDC25 session 249](https://developer.apple.com/videos/play/wwdc2025/249/)

**Apple: notifications, grace period, billing retry, refunds, family sharing**
- ASSN V2 `notificationType` values: SUBSCRIBED (INITIAL_BUY / RESUBSCRIBE), DID_RENEW (BILLING_RECOVERY), DID_FAIL_TO_RENEW (GRACE_PERIOD subtype = keep service; empty = billing retry without grace), GRACE_PERIOD_EXPIRED, EXPIRED (VOLUNTARY / BILLING_RETRY / PRICE_INCREASE / PRODUCT_NOT_FOR_SALE), DID_CHANGE_RENEWAL_STATUS, DID_CHANGE_RENEWAL_PREF, OFFER_REDEEMED, PRICE_INCREASE, REFUND (includes `revocationDate`, `revocationReason`), REFUND_DECLINED, REFUND_REVERSED (restore access), CONSUMPTION_REQUEST, REVOKE, RENEWAL_EXTENDED / RENEWAL_EXTENSION, ONE_TIME_CHARGE, RESCIND_CONSENT (a parent withdrew consent for a child's use), EXTERNAL_PURCHASE_TOKEN, TEST, and Advanced-Commerce-only METADATA_UPDATE / MIGRATION / PRICE_CHANGE (23 values in total) — [Apple: notificationType](https://developer.apple.com/tutorials/data/documentation/appstoreservernotifications/notificationtype.json)
- **REVOKE** is sent when the purchaser stops Family Sharing, a member leaves the family, or a refund is issued. Family members who gain access arrive as SUBSCRIBED or ONE_TIME_CHARGE. Billing retry lasts **up to 60 days**. After GRACE_PERIOD_EXPIRED we may cut access while retries continue — [Apple: notificationType](https://developer.apple.com/tutorials/data/documentation/appstoreservernotifications/notificationtype.json)
- Billing Grace Period is set in App Store Connect at **3, 16, or 28 days**, for all renewals or only paid renewals. If recovered within grace, "there won't be any interruption to the days of paid service or to your revenue." On iOS 16.4+ a system sheet asks users to update payment, and StoreKit messages can delay or suppress it. Family Sharing covers up to 5 members, **"can't be undone"** once enabled, and `ownershipType` tells purchaser from family member — [Apple: Auto-renewable subscriptions](https://developer.apple.com/app-store/subscriptions/)
- Refund decisions: CONSUMPTION_REQUEST asks us for consumption data, and we answer through the Send Consumption Information endpoint. Get Refund History lists a customer's refunds — [Apple: notificationType](https://developer.apple.com/tutorials/data/documentation/appstoreservernotifications/notificationtype.json)

**Apple: sandbox vs. production**
- Developers quote Apple's documented lookup order: call the **production** endpoint first. On `4040010 TransactionIdNotFoundError`, call **sandbox**. If both fail, the ID exists in neither. The older error code 4040005 was replaced in API v1.8 — [Apple Developer Forums 848630](https://developer.apple.com/forums/thread/848630)
- Before the app has a production release, production App Store Server API calls return 401: "until you have a release in production, access to the production APIs is not allowed" — [Apple Developer Forums 757719](https://developer.apple.com/forums/thread/757719)
- A developer reports that a purchase made during App Review returned 4040010 from production and asks whether routing to sandbox is supported. In the excerpt found, Apple had not answered — [Apple Developer Forums 848630](https://developer.apple.com/forums/thread/848630)
- Fresh transaction IDs sometimes return 4040010 for 2–5 minutes before they can be queried — [Apple Developer Forums 818605](https://developer.apple.com/forums/thread/818605)

**Google Play: binding, uniqueness, acknowledgement, revocation**
- "purchaseToken is globally unique, so you can safely use this value as a primary key." Do **not** use `orderId` for deduplication: promo-code purchases have no orderId — [Android Developers: Fight fraud and abuse](https://developer.android.com/google/play/billing/security)
- If `obfuscatedAccountId` / `obfuscatedProfileId` were set in `BillingFlowParams`, "check that the purchase mapping matches the expected user account in your system". Google also uses these IDs to detect fraud — [Android Developers: Fight fraud and abuse](https://developer.android.com/google/play/billing/security)
- When `linkedPurchaseToken` is set, remove the linked token and **revoke its entitlement** "to ensure that multiple users are not entitled for the same purchase". Grant only when the state is PURCHASED, never PENDING. If a purchase fails validation, do not acknowledge it; call `purchases.subscriptionsv2:revoke` with `"fullRefund": {}` instead. Use the Voided Purchases API for refunds and chargebacks (possible responses: claw back, warnings for first offenders, temporary purchase blocks) — [Android Developers: Fight fraud and abuse](https://developer.android.com/google/play/billing/security)
- Acknowledge within **3 days** or the user is automatically refunded and the purchase revoked. Server-side acknowledgement is recommended. A plan change is blocked while the current subscription is unacknowledged — [Android Developers: Subscription lifecycle](https://developer.android.com/google/play/billing/lifecycle/subscriptions)
- On every RTDN, call `purchases.subscriptionsv2.get`, "the source of truth". States and access: ACTIVE and IN_GRACE_PERIOD grant; CANCELED grants until `expiryTime`; ON_HOLD, PAUSED, and EXPIRED revoke. SUBSCRIPTION_REVOKED (refund, chargeback, or revoke API) revokes immediately. SUBSCRIPTION_RESTARTED restores on the same token — [Android Developers: Subscription lifecycle](https://developer.android.com/google/play/billing/lifecycle/subscriptions)
- Defaults: grace period on, length set in Play Console; a "silent grace period" of at least 1 day during which the state stays ACTIVE and no RTDN is sent; account hold on, default **60 days minus the grace period**; pause allowed by default; purchase token usable until **60 days after expiry**. A resubscribe from the Play Store after expiry carries `outOfAppPurchaseContext` (`expiredExternalAccountIdentifiers`, `expiredPurchaseToken`) to re-link the user. Re-signing up for the same base plan before expiry creates a $0.00 order, which is not a trial — [Android Developers: Subscription lifecycle](https://developer.android.com/google/play/billing/lifecycle/subscriptions)
- RevenueCat's 2026 benchmark: billing errors cause **31% of Google Play cancellations** (14% on the App Store), so grace and hold handling matters — [RevenueCat SOSA 2026 summary](https://www.revenuecat.com/blog/growth/subscription-app-trends-benchmarks-2026)

**If RevenueCat is used**
- The default "Transfer to new App User ID" moves a restored receipt to whoever restores it, so the previous account loses access. "Keep with original App User ID" blocks a restore under another ID with an error. RevenueCat warns that combining server-to-server purchase tracking with the non-default modes can leave customers without entitlements — [RevenueCat docs: restore behavior](https://www.revenuecat.com/docs/projects/restore-behavior)

### Inferences
- **One receipt, many accounts.** The attack: user A buys, logs out, logs in as B, taps Restore. Defenses: (a) unique DB constraint on `apple_original_transaction_id` and `google_purchase_token` (plus linked-token chains); (b) on restore, if the token belongs to another user, either *transfer* (simple, matches RevenueCat's default) or *reject and show "this subscription is linked to another account (e•••@…)"*. For a login-required app, a reasonable choice is "transfer only if the previous owner's entitlement is inactive". Otherwise transfer and log it, because Apple ties the subscription to the Apple ID, not to our account. (c) Always set `appAccountToken = user.subscriptionUuid` (a stable random UUID stored on the user row, never derived from email or phone), and on the server compare the decoded `appAccountToken` with the requesting user. (d) For offer-code purchases made in the App Store, call Set App Account Token after the first in-app restore.
- **Idempotency.** Store every raw ASSN V2 `signedPayload` and RTDN Pub/Sub message, keyed by Apple `notificationUUID` and Pub/Sub `messageId`. Return 2xx fast, process in a queue (e.g. BullMQ in NestJS), and re-fetch state (Get All Subscription Statuses / `subscriptionsv2.get`) instead of applying deltas. Order is not guaranteed, so compare `signedDate` / event time and never let an older event overwrite newer state. Add a daily reconciliation cron for active subscriptions near expiry. (The notificationUUID field and Pub/Sub at-least-once delivery come from general knowledge of these APIs. Their docs were not fetched in this session.)
- **Sandbox handling.** The production backend must accept sandbox transactions, or App Review will see a broken purchase and reject under 2.1(b). Use the production-then-sandbox fallback, record `environment` on each entitlement, and consider limiting sandbox entitlements to known test or review accounts, or expiring them quickly, so TestFlight "free" purchases cannot unlock production accounts permanently. Configure separate production and sandbox ASSN URLs in App Store Connect.
- **Grace period / billing retry.** Enable Apple Billing Grace Period (16 days is a common middle setting) and keep Play's default grace. Keep access during grace, show an in-app "update payment" banner, and cut access on GRACE_PERIOD_EXPIRED or ON_HOLD. Restore on DID_RENEW(BILLING_RECOVERY) or SUBSCRIPTION_RECOVERED.
- **Refunds and revocations.** Revoke on Apple REFUND / REVOKE and Google SUBSCRIPTION_REVOKED / voided purchases, and restore on REFUND_REVERSED. Answer CONSUMPTION_REQUEST honestly. AI-usage data (scans and chats used) is legitimate "consumption" evidence.
- **Family Sharing.** Our recommendation is to leave it **off** at launch. Enabling cannot be undone, appAccountToken cannot be set on FAMILY_SHARED transactions, and every family member would need their own account mapping, while per-user AI costs multiply.

## 3. Store rules for an AI plant app (App Store Review Guidelines, Google Play policies)

### Takeaway
The App Store Review Guidelines were **last updated 2026-10-16**. The rules that matter most for us: 3.1.1/3.1.2 (IAP only, ongoing value, clear terms before subscribing), 5.1.1(v) (in-app account deletion), 4.8 (an *equivalent privacy-focused login*, in practice Sign in with Apple, if Google login is offered), 5.1.2(i) (explicit consent before sending personal data to **third-party AI**, since 2025-11-13), 1.2 (AI content creation apps need filtering, reporting, and blocking), and 2.1 (demo account, working IAP). On Google Play: the Subscriptions policy, account deletion (in-app path plus a web link), Data safety, the AI-Generated Content policy (in-app reporting of offensive output), target API 36, and PBL 8+. The 12-tester / 14-day closed-test rule applies to **personal** accounts created after 2023-11-13. A Turkish company (organization) account appears exempt but needs a D-U-N-S number.

### Cited Findings

**Apple App Review Guidelines (page "Last Updated: October 16, 2026")** — [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- **3.1.1 In-App Purchase:** unlocking features (including subscriptions) must use IAP. No license keys, QR codes, or crypto. "Restorable purchases need a restore mechanism."
- **3.1.2(a) Subscriptions:** "must provide ongoing value", last at least 7 days, and be available on all of the user's devices. Listed examples include consistently updated apps, SaaS, and cloud support. **3.1.2(b):** no accidental subscription to several variants of the same thing. **3.1.2(c):** before asking a customer to subscribe, clearly describe what they get for the price, and meet Schedule 2 of the Apple Developer Program License Agreement.
- **3.1.3:** no in-app steering to non-IAP purchasing except on the US storefront (and the 3.1.1(a)/3.1.3(a) cases).
- **2.1 App Completeness:** if the app has a login, supply demo account info and keep the backend live. A built-in demo mode needs Apple's prior approval. **2.1(b):** IAPs must be complete, visible to the reviewer, and working. If one cannot be found, explain why in review notes.
- **1.4.1 Medical:** apps that could give inaccurate data, or be used to diagnose or treat *patients*, get more scrutiny. Accuracy claims need disclosed methodology. Apps should remind users to consult a doctor.
- **1.2 User-Generated Content:** explicitly includes **"AI content creation apps"**, which need a filter for objectionable material, a way to report offensive content with timely responses, the ability to block abusive users, and published contact information.
- **4.5.4 Push:** the app must not require push to function. No sensitive data in pushes. Promotional push only with explicit in-app opt-in consent and an in-app opt-out.
- **4.8 Login Services:** if a third-party or social login (e.g. Google Sign-In) sets up or authenticates the primary account, the app must also offer an equivalent login that limits data to name and email, lets users keep their email private, and does not collect interactions for ads without consent. The current text does not name "Sign in with Apple". Exemptions include apps that use only the company's own account system.
- **5.1.1(i)–(v):** a privacy policy linked in App Store Connect and in the app (data, uses, third parties, retention and deletion). Consent before collection. Data minimization. No forced consent. **(v):** if the app lacks significant account-based features, allow use without login. If it supports account creation, it **must offer account deletion within the app**.
- **5.1.2(i):** "clearly disclose where personal data will be shared with third parties, **including third-party AI**, and obtain explicit permission before doing so." Apps may not require users to enable system features (push, location, tracking) to get functionality.
- **5.6 Code of Conduct:** apps must not "trick them into making unwanted purchases… raise prices in a tricky manner, charge for features or content that are not delivered". 5.6.4: excessive customer complaints or refund requests count against the developer.
- The **5.1.2(i) third-party-AI wording was added on 2025-11-13**, the first time Apple named AI in its privacy rules. Secondary coverage notes Apple has not said whether on-device versus cloud AI is covered — [iGeeksBlog](https://www.igeeksblog.com/apple-app-store-ai-data-disclosure-guidelines); [ppc.land](https://ppc.land/apple-tightens-app-store-age-controls-and-data-sharing-disclosure/)
- **Age ratings:** new tiers 4+/9+/13+/16+/18+. The updated questionnaire (in-app controls, capabilities, medical or wellness topics, violence) had to be answered by **2026-01-31** or updates are blocked. Developers must account for features "including AI assistants and chatbot functionality" when rating sensitive-content frequency — [9to5Mac 2025-07-24](https://9to5mac.com/2025/07/24/apple-notifies-developers-of-new-app-store-age-rating-system/); [ppc.land](https://ppc.land/apple-updates-app-store-age-ratings-system-with-granular-controls/)

**Apple subscription sign-up screen requirements** — [Apple: Auto-renewable subscriptions](https://developer.apple.com/app-store/subscriptions/)
- Must show: subscription name, duration, and content or services; "Full renewal price, shown clearly and prominently, and localized"; "A way for current subscribers to sign in or restore purchases"; links to **Terms of Use and Privacy Policy** in the app *and* in App Store metadata.
- "The amount that will be billed must be the most prominent pricing element." Monthly-equivalent or savings breakdowns must be "subordinate" in position and size to the annual price.
- Free trials: "clearly indicate how long the free trial lasts and the price billed once the free trial is over."
- Always make the system management UI easy to reach (`showManageSubscriptions(in:)`).

**Apple organization enrollment (Turkish company)** — [Apple Developer Program: Enroll](https://developer.apple.com/programs/enroll/)
- Needs a legal entity (no DBAs or branches), legal binding authority, a **D-U-N-S Number**, a work email on the organization's domain, a public and functional website on that domain, and an Apple Account with 2FA under the person's legal name. Fee: $99/year (local currency shown). The organization name appears as the seller on the App Store.

**Google Play**
- **Subscriptions policy:** disclose offer terms, cost, billing frequency, auto-renewal, and whether a subscription is required to use the app, without extra steps from the user. Subscriptions must give sustained or recurring value. Trials must state duration, price, content, how and when they convert, and how to cancel before conversion. All pricing and terms must be localized. A cancel/manage link must be in account settings (the Play Subscription Center link is fine). Default Play policy: no refund for the current period. Listed violations include: annual plans that prominently show a monthly price, SKUs named "Free Trial" that auto-charge, missing or unclear dismiss buttons, intro price without the post-intro price, trial-end charges hard to read, repeated taps in one spot leading to accidental subscription, and value that drops sharply after the first period — [Play Console Help: Subscriptions](https://support.google.com/googleplay/android-developer/answer/9900533)
- **Account deletion:** apps that allow account creation must (1) let users start account and data deletion **in the app** and (2) provide a **web link** where deletion can be requested without reinstalling. The link is declared in the **Data safety** form, and the store listing shows a data-deletion badge. Deletion covers all data types declared as collected, and providers should be asked to delete shared data. Retention for fraud or legal reasons must be disclosed. Enforcement (including removal) has been possible since after 2024-05-31 — [Play Console Help: account deletion](https://support.google.com/googleplay/android-developer/answer/13327111)
- **Testing requirement:** personal accounts created after **2023-11-13** need **≥12 testers continuously opted in for 14 days** in a closed test before applying for production. The application asks about recruitment, feedback, changes made, target audience, value proposition, and expected first-year installs. Review usually takes ≤7 days — [Play Console Help 14151465](https://support.google.com/googleplay/android-developer/answer/14151465)
- **Organization accounts:** Google's page scopes the rule to personal accounts and does not mention organizations. Secondary guides say organization accounts are exempt and need a D-U-N-S number (reported times range from ~5 business days to 30 days) — [extendsclass](https://extendsclass.com/blog/google-plays-closed-testing-requirement-what-developers-need-to-know-in-2026); [choicely](https://www.choicely.com/blog/google-play-12-tester-rule)
- **AI-Generated Content policy:** covers apps that generate content from text, voice, or image prompts, including "text-to-text chatbot apps where the AI chat is a central feature". Bans include content encouraging harmful behavior and deceptive content. Developers "are responsible for ensuring that their generative AI apps do not generate offensive content" — [Play Console Help 14094294](https://support.google.com/googleplay/android-developer/answer/14094294). Google announced in Oct 2023, and confirmed in June 2024, that such apps must let users **report or flag offensive AI output without leaving the app** — [MediaNama](https://www.medianama.com/2023/10/223-google-play-content-reporting-policy-ai-apps/); [Android Developers Blog 2024-06](https://android-developers.googleblog.com/2024/06/enabling-safe-ai-experiences.html?hl=zh_CM)
- Target API 36 and PBL 8+ deadlines: see section 1.

### Inferences
- **AI chat triggers 1.2 / AI-Generated Content.** Add a "Report this answer" control on every AI message and diagnosis result, a server-side moderation pass on LLM output (Claude/OpenAI moderation or a classifier), contact info in the app and store listing, and a system prompt that refuses off-topic or harmful requests (e.g. pesticide misuse, toxicity to pets or humans). Plant toxicity and pesticide advice is the "health-like" risk area. 1.4.1 targets *human* medical diagnosis, so plant "diagnosis" should not trigger it, but avoid human-health claims ("treats your allergies") and add disclaimers for toxicity and chemical-treatment advice ("consult an expert; follow the product label").
- **5.1.2(i) consent screen.** Plant photos, chat text, and possibly location go to a third-party LLM or vision API. Add an explicit in-app consent step naming the provider category ("photos and messages are sent to [provider] to generate answers") before the first scan or chat, with a link to the privacy policy. Mirror this in the Data safety form ("shared with third parties: photos, app activity").
- **Login.** Offering Google Sign-In on iOS requires an equivalent privacy-focused option. In practice that means **Sign in with Apple** (it meets all three criteria). Email/password alone (our own account system) is exempt. Because the app is account-based (synced plants, chat history, subscription binding), requiring login is defensible under 5.1.1(v). Still, letting users try identification before signup lowers friction and review risk.
- **Account deletion.** It must be one in-app flow (Settings → Delete account) that deletes server data (NestJS + storage + LLM logs where possible), plus a public web page for Google. Tell users that deletion does **not** cancel the store subscription, and link to Apple and Play subscription management.
- **Review package (Apple).** Demo account credentials with an active or sandbox-purchasable state, review notes explaining the AI features and where the paywall and restore button are, IAP products submitted with the binary (first subscription must be attached to a version), screenshots of the paywall, and Terms (EULA) and Privacy links in both metadata and the paywall.
- **Turkish company on Play.** An organization account skips the 12×14 closed test (per secondary sources) but needs D-U-N-S and organization verification. Running a closed test with real Turkish users is still worthwhile for feedback and Data safety accuracy.
- **3.1.2(a) ongoing value.** An AI plant app with a continually updated plant database, ongoing AI diagnosis and chat, reminders, and cloud sync clearly qualifies ("SaaS, cloud support, consistently updated apps"). Avoid putting purely one-time content (e.g. a static e-book) behind the subscription.

## 4. Paywall and trial best practices (benchmarks)

### Takeaway
2026 data favors a **hard paywall or strong onboarding paywall**: about 5× higher download-to-paid and about 8× higher revenue per install versus freemium, with similar year-1 retention. Weekly plans now earn the majority of subscription revenue industry-wide. For trials, **longer trials (≥10 days) convert and retain better on annual plans**, but most cancellations of short trials happen on day 0–1. AI apps earn about 41% higher year-1 LTV but monthly plans churn faster. Apple and Google both forbid making the per-month breakdown more prominent than the amount actually billed.

### Cited Findings
- RevenueCat **State of Subscription Apps 2026** (published 2026-03-19, updated 2026-04-22; 115,000+ apps, $16B+ revenue, 338-page report) — [RevenueCat SOSA 2026 summary](https://www.revenuecat.com/blog/growth/subscription-app-trends-benchmarks-2026):
  - Hard paywall vs. freemium: Day-35 conversion median **10.7% vs. 2.1%** (about 5×; hard was 12.1% in 2025). The blog labels this "trial-to-paid" in places; it matches the download-to-paid metric of the 2025 report. Revenue per install at day 60: **$3.09 vs. $0.38** (about 8×). Year-1 retention of yearly subscribers: freemium 28% vs. hard 27%.
  - Trials: **55.4% of 3-day-trial cancellations happen on Day 0** and 84% on Day 0–1. Trials of 17–32 days convert at a median **42.5%** vs. **25.5%** for trials under 4 days. The share of apps using trials under 4 days rose to 46.5% (from 42.1%).
  - Annual plans: 35% of annual cancellations happen in Month 1. About **72% of annual subscribers cancel in year 1** in 2026 (about 56% in 2025).
  - Billing errors cause 31% of Google Play cancellations vs. 14% on the App Store.
  - **AI apps:** year-1 realized LTV $30.16 vs. $21.37 for non-AI apps (+41%), but AI **monthly** plans retain 36% worse over 12 months.
  - Top-quartile apps grew MRR 80%+ YoY. The bottom quartile shrank more than 33%.
- SOSA 2026 category pages — [RevenueCat SOSA 2026 Utilities](https://www.revenuecat.com/state-of-subscription-apps-2026-utilities/):
  - Utilities (Weather, Reference, Utilities, Finance, Tools): D30 download-to-trial median **6.5%**. Trial-to-paid is "highly variable".
  - Social & Lifestyle: **43.6% of apps use no trial** (highest of any category), the highest weekly-plan share, and a monthly median price of **$9.99**.
  - Global: median D35 download-to-paid **2.0%**. Median trial-to-paid is **34.2% in North America vs. 15.2% in India/SEA**, a large regional gap.
- RevenueCat "Free trial length" (2026-09-28), top 100 apps per category — [RevenueCat blog: free trial length](https://www.revenuecat.com/blog/growth/free-trial-length):
  - Weekly plans: trials of ≤4 days dominate (81–100%). Trial-to-paid is 22.3% (≤4 days) vs. 24.3% (5–9). First renewal 57.9% vs. 65.9%.
  - Annual plans: trial-to-paid **24% (≤4) / 33% (5–9) / 43% (10–16) / 44.6% (17–32)**. First renewal **18.3% / 25.3% / 36.4% / 47.5%**. Annual no-trial renewal 26.6%.
  - Monthly plans: trial-to-paid 39.6% / 45.9% / 46.6% / 43.7%. Renewal 54.2% / 62.8% / 72.0% / 77.5%.
  - AI apps, annual plans: no-trial renewal 18.9% vs. 15.1% (≤4-day trial) vs. 19.6% (5–9).
  - Advice: do not copy category leaders. Test trial length against time-to-value and habit formation.
- **Adapty State of In-App Subscriptions 2026** (16,000+ apps, $3B+, 2025 data, mostly App Store) — [Adapty blog](https://adapty.io/blog/mobile-app-monetization-2026/); [Adapty: weekly vs monthly vs annual](https://adapty.io/blog/weekly-monthly-annual-subscription-plan/); [Airbridge summary](https://www.airbridge.io/en/blog/weekly-vs-annual-subscription-app); [Adapty report page](https://adapty.io/state-of-in-app-subscriptions/); [ppc.land](https://ppc.land/95-of-app-subscription-revenue-goes-to-top-10-adaptys-2026-benchmark-report/):
  - Revenue share by plan: **weekly 55.5%** (43.3% in 2023), annual 22.5% (29.2%), monthly 11.7% (21.1%).
  - Install-to-trial at upper-mid pricing: weekly 9.8% vs. annual 1.8% vs. monthly 0.3%.
  - 12-month LTV: weekly with trial $54.50 vs. weekly without trial $7.40. Annual with trial $49.92 by day 380.
  - Health & Fitness is the one category where annual plans dominate (60.6% of revenue).
- Apple offer tooling — [Apple: Auto-renewable subscriptions](https://developer.apple.com/app-store/subscriptions/):
  - Introductory offers (free trial, pay as you go, pay up front) are set per territory, with one per subscription group per customer.
  - Promotional offers: up to 10 per subscription, for existing or lapsed subscribers.
  - **Win-back offers** for past subscribers appear on the product page, in an automatic in-app sheet, and in Subscription settings. "Streamlined purchasing" is on by default.
  - Offer codes come as 18-digit one-time codes or custom codes. The app must be live to redeem them.
  - Price increases: Apple notifies users. Larger increases need opt-in, and non-consenting subscriptions expire. Existing subscribers can be kept at their old price.
- Paywall disclosure rules (both stores): see section 3. Both forbid making the monthly-equivalent figure more prominent than the billed annual price, and require trial length plus the post-trial price — [Apple subscriptions](https://developer.apple.com/app-store/subscriptions/); [Play Subscriptions policy](https://support.google.com/googleplay/android-developer/answer/9900533)

### Inferences
- **Paywall model for the MVP:** an onboarding paywall shown after the first "aha" moment (a successful identification) with a visible close (X). This is effectively a "soft-hard" paywall: limited free scans (e.g. 1–3 per day or week), with AI chat, diagnosis, and unlimited reminders behind the paywall. A true hard paywall (no free use) earns the most revenue per install in benchmarks, but Google lists unclear dismiss buttons as a violation. A plant app's first value (identification) is also its best marketing hook, so 1–3 free IDs is a reasonable middle ground to A/B test.
- **Plans:** annual (primary, with trial) plus weekly or monthly as the anchor and alternative. Industry data favors weekly for revenue. Turkish purchasing power and lower trial-to-paid in emerging markets (IN/SEA 15.2% vs. NA 34.2%) suggest a well-localized TRY price and possibly a monthly plan instead of a premium weekly. Use Apple and Google local price tiers rather than straight USD conversion.
- **Trial:** for an annual plan, a 7-day trial is the common default. Data says 10–16-day trials convert and renew notably better (43% / 36.4%), so A/B test 7 vs. 14 days. Because most short-trial cancellations happen on day 0, deliver value on day 1–2 of the trial (reminder setup, first diagnosis) and send a pre-renewal reminder notification (good for trust and refund rates).
- **AI cost control:** AI apps earn higher LTV but have high variable cost. Keep scan and chat quotas server-side even for paying users (fair-use), and expose a usage meter in the UI.
- **Win-back:** set Apple win-back offers (shown automatically) and Google Play winback/resubscribe offers. Use offer codes for Turkish influencer campaigns. Make sure appAccountToken is set after an offer-code redemption (section 2).

### Gaps
- No plant-app-specific or Turkey-specific conversion benchmarks found (e.g. TRY price points, Turkish trial-to-paid). The full SOSA 2026 PDF has by-country data that was not accessed.
- Exact Utilities/Lifestyle trial-to-paid, price, and refund figures sit in the full report, not in the pages read.
- Did not research competitor paywalls (PictureThis, Plantum, Planta) for current trial and price setups.

## 5. Care-reminder notifications in Expo (expo-notifications) and store rules on permission prompts

### Takeaway
Watering and fertilizing reminders should be **local notifications scheduled on the device** with expo-notifications, with remote push (Expo Push or FCM/APNs from NestJS) reserved for server-driven messages. Design around iOS's **64 pending-request cap** and Android 12+/14+ exact-alarm restrictions. Never require notification permission to use the app (Apple 4.5.4, 5.1.2(i)). Ask in context, and on Android 13+ create a notification channel before the prompt.

### Cited Findings
- **Expo Go vs. dev builds:** local notifications work in Expo Go. Remote push does not work in Expo Go on Android from SDK 53 on, so a dev build is needed — [Expo docs: Notifications](https://docs.expo.dev/versions/latest/sdk/notifications/)
- **Triggers:** TIME_INTERVAL (optionally repeating) and DATE (both platforms). DAILY, WEEKLY, MONTHLY, YEARLY are Android-only; CALENDAR is iOS-only (it can repeat); region triggers are iOS-only. DAILY, DATE, and MONTHLY default to `delivery: 'bestEffort'` — [Expo docs: Notifications](https://docs.expo.dev/versions/latest/sdk/notifications/)
- **Android 13+:** users must opt in through a system prompt, and the prompt **does not appear until at least one notification channel exists**. Call `setNotificationChannelAsync` first — [Expo docs: Notifications](https://docs.expo.dev/versions/latest/sdk/notifications/)
- **Exact alarms:** `SCHEDULE_EXACT_ALARM` is needed on Android 12+, and on Android 14+ it is **denied by default for new installs**. Check and request with `getExactAlarmPermissionsAsync` / `requestExactAlarmPermissionsAsync`. Without it, notifications arrive at an approximate time and `alarmClock` delivery falls back to bestEffort. `USE_EXACT_ALARM` (granted without a prompt) is limited by Google Play to alarm, timer, and calendar apps — [Expo docs: Notifications](https://docs.expo.dev/versions/latest/sdk/notifications/)
- **Reboot:** Expo adds `RECEIVE_BOOT_COMPLETED` so scheduled notifications are restored after restart. Doze mode or too many notifications can still suppress delivery (Apple recommends no more than 2–3 per hour). Background notification tasks need `expo-task-manager`, plus `remote-notification` background mode and `contentAvailable` on iOS — [Expo docs: Notifications](https://docs.expo.dev/versions/latest/sdk/notifications/)
- **Permissions API:** `requestPermissionsAsync`. On iOS, read `ios.status` (NOT_DETERMINED / DENIED / AUTHORIZED / PROVISIONAL / EPHEMERAL). `allowProvisional` gives quiet provisional delivery — [Expo docs: Notifications](https://docs.expo.dev/versions/latest/sdk/notifications/)
- **SDK 58 changes:** foreground notifications show by default; Android `delivery: 'alarmClock'`; iOS `threadIdentifier` grouping; `largeIcon` in the config plugin — [Expo SDK 58 changelog](https://expo.dev/changelog/sdk-58)
- **iOS 64 limit:** Apple docs, as quoted in forums, say the system keeps the 64 soonest-firing pending requests and drops the rest. A repeating trigger counts as one. An Apple engineer confirmed there is no workaround — [Apple Developer Forums 811171](https://developer.apple.com/forums/thread/811171); [Apple Developer Forums 765490](https://developer.apple.com/forums/thread/765490). Pending requests stay until they fire or are removed (`removePendingNotificationRequests(withIdentifiers:)`) — [Apple: Scheduling a notification locally](https://developer.apple.com/tutorials/data/documentation/usernotifications/scheduling-a-notification-locally-from-your-app.json)
- **Store rules:**
  - Apple 4.5.4: the app must not require push to work. No sensitive info in pushes. Marketing pushes need explicit in-app opt-in and an in-app opt-out — [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
  - Apple 5.1.2(i): apps may not require enabling system features such as push to access functionality — [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
  - Apple subscription guidance: notifications must be "timely, serve a clear purpose, and deliver meaningful information" — [Apple: Auto-renewable subscriptions](https://developer.apple.com/app-store/subscriptions/)

### Inferences
- **Architecture:** NestJS holds the care schedule (source of truth, synced across devices). On app open, app foreground, and each schedule change, the app cancels and reschedules **only the next N reminders** (e.g. 7–14 days, ≤ ~50 requests, leaving headroom under 64). Use one aggregated "3 plants need water today" reminder per day instead of one per plant, which also respects the "2–3 per hour" guidance. On iOS use a CALENDAR repeating trigger per routine (counts as one request); on Android use DAILY/WEEKLY.
- **Remote push** (Expo Push Service or direct FCM/APNs from NestJS) only for server-side events: AI diagnosis finished, a re-engagement nudge if the user has not opened the app for a while (marketing needs opt-in under 4.5.4), and subscription billing-issue alerts. Keep plant names generic in payloads.
- **Exact alarms:** watering does not need minute precision. Use bestEffort/inexact delivery and do **not** declare `USE_EXACT_ALARM`; plant care is not an alarm or calendar app, so declaring it risks Play policy trouble. Ask for `SCHEDULE_EXACT_ALARM` only if user testing shows unacceptable drift.
- **Permission UX:** show a pre-permission explainer right after the user adds a first plant or sets a reminder, not at cold start. Create the Android channel at app start so the prompt can appear. Consider iOS provisional authorization for quiet first reminders. If denied, keep the in-app task list working (4.5.4) and offer a Settings deep link.
- **Subscription interplay:** reminders should stay free (or partly free) as a retention hook. A pre-trial-end local reminder ("your trial ends tomorrow") is user-friendly and lowers refunds and complaints (5.6.4 counts complaints against the developer).
